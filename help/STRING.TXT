=== STRING - text handling ===

Strings live on a heap and are garbage-collected, so they can be built
and thrown away freely. A string variable's name ends in "$".

[x] LEN(s$) - length in characters.
[x] LEFT$(s$,n) - the first n characters.
[x] RIGHT$(s$,n) - the last n.
[x] MID$(s$,start,len) - len characters from start. START COUNTS FROM
    ZERO on this BASIC, which is not what most of them do. See below.
[x] CHR$(n) - the character with code n. CP437, so CHR$(65) is "A".
[x] ASC(s$) - the code of the first character.
[x] STR$(n) - a number as text. It keeps the classic leading space for a
    non-negative value, so LEN(STR$(7)) is 2, not 1.
[x] VAL(s$) - text as a number.
[x] HEX$(n) - a number as hexadecimal, no "$" prefix. HEX$(255) is "FF".
[x] DEC(s$) - a hexadecimal string as a number, the inverse of HEX$.
[x] s$ + t$ - join two strings.
[x] = <> < > <= >= - compare two strings, in character-code order.
[x] TAB(n) and SPC(n) - column and spacing control inside PRINT.

MID$ IS ZERO-BASED. MID$("HELLO",0,2) is "HE" and MID$("HELLO",2,3) is
"LLO", where almost every other BASIC would give "HE" for MID$(s$,1,2)
and "ELL" for MID$(s$,2,3). It is inherited from BASIC816 and it will
trip up anyone typing in a listing from a book. Worth deciding
deliberately: either change it to one-based and say so loudly, or keep it
and make sure it is the first line of this page - which for now it is.

Nothing below exists. These are the string functions a BASIC is expected
to have and this one does not, in roughly the order they are missed:

[x] INSTR(s$,find$) - position of a substring. ZERO-BASED, and -1 when
    absent, rather than the usual 1-based-with-0-for-absent: MID$ counts
    from zero here, so INSTR has to as well or its result cannot be
    handed straight to it. MID$(s$, INSTR(s$,f$), n) means what it looks
    like. An empty needle is found at 0. A start offset is not accepted
    yet.
[x] UCASE$(s$) - upper case. Only a-z move: CP437's accented letters are
    not a fixed distance from their capitals, so shifting them by 32
    would produce unrelated glyphs.
[ ] LCASE$(s$) - written, and then taken back out. No token left. See
    below.
[x] TRIM$(s$) - strip leading and trailing spaces. INPUT hands back
    exactly what was typed, so comparing it usually wants this first.
    LTRIM$/RTRIM$ for the halves separately are not here.
[ ] STRING$(n,c$) - n copies of a character, for rules and bar charts.
    Written, and then taken back out. No token left.
[ ] SPACE$(n) - n spaces. Same.
[ ] REPLACE$(s$,old$,new$) - substitution.
[ ] SPLIT / JOIN into a string array - parsing a line of input is the
    single most common thing a beginner's program does with text.
[ ] BIN$(n) and its inverse - handy next to HEX$ when poking hardware
    bits, which on this machine is most of what HELP says to do.

THE TOKEN TABLE IS FULL, and that is now the limit on this whole
directory rather than anything about strings. A token is a byte with bit
7 set, so there are exactly 128 of them and this build uses every one.
LCASE$, STRING$ and SPACE$ were written, did not fit, and were removed
again; they are in the history of src/superbasic.s.

Everything still unticked across these pages -- sprites, sound,
graphics, the palette, the joystick -- wants keywords too, so the next
real piece of work is a two-byte token scheme: reserve one id as an
escape and let its successor select from a second table. Every consumer
of a token id has to learn it (TOKTYPE, TOKEVAL, TOKPRECED, TOKARITY,
the "is it a token" tests, and LIST). tokens.s now fails the build with
a clear message rather than an arithmetic overflow when the 129th
arrives.

A note on memory. Building strings in a loop allocates, and the heap is
in banks $02-$04 with the program text (HELP MEMORY). Long loops of
s$ = s$ + x$ will collect garbage; that is normal for a BASIC, but on
this machine there is a lot of SDRAM sitting unused behind the kernel's
allocator, and moving the string heap out there is an option worth
remembering if it ever becomes the limit.
