=== MEMORY - peeking, poking and where things live ===

The 65816 addresses all sixteen megabytes flat. There is no bank
register, no $A000 window, none of the C64 or X16 banking machinery -
an address here is 24 bits and that is all there is to it.

[x] PEEK(addr) - read a byte.
[x] POKE addr,value - write one.
[x] PEEKW(addr) / POKEW addr,value - 16-bit.
[x] PEEKL(addr) / POKEL addr,value - 24-bit.
[ ] MEMCOPY src,dst,len - block copy. Reserved, refuses today; would be
    the place to use the blitter or a hardware fill, HELP VERAFX.
[x] FRE - bytes still free for the program, its variables and the heap.
    Takes no parentheses; classic BASICs want a dummy argument and throw
    it away, and there is nothing here to throw away.

    ONE NUMBER, because there is one space. Variables grow UP from the
    end of the program and strings grow DOWN from the top of BRAM, and
    they meet in the middle - the subtraction this reports is exactly
    the collision check that refuses a new variable, which is why it is
    the honest number and not a sum of two pools.

    It counts nothing the garbage collector could reclaim, so it is a
    floor and not a promise.
[ ] ALLOC(size) / FREE addr - grab a block of SDRAM from the kernel
    (K_MEM_ALLOC). The arena is huge and the allocator has a 32-block
    cap, so the pattern is one big block sub-allocated by hand.
[ ] VPEEK(addr) / VPOKE addr,value - VERA's own 128 KB of VRAM, which
    is NOT in the CPU address space: it is reached through a port at
    $9F20-$9F23. Tiles, sprite pixels and the VERA palette all live
    there, so graphics statements need this even if users never do.

Addresses worth knowing, from X816_core/doc/MEMORY_MAP.md:

    $00:0000-$00:9EFF   bank-0 BRAM: direct page, CPU stack, our globals
    $00:9F00-$00:9FFF   I/O page - VIA, VERA, YM2151, SYSCTL, SD, timer
    $00:A000-$00:FEFF   more bank-0 RAM
    $00:FE00-$00:FEFF   the kernel jump table (inside that RAM)
    $01:0000-$04:FFFF   256 KB single-cycle BRAM. SuperBasic's code is in
                        $01; your program text and heap follow, to $04:FFFF
    $05:0000-$EF:FFFF   about 14.7 MB of SDRAM
    $E0:0000            the VERA2 framebuffer, HELP GRAPHIC
    $10:0000            do NOT park data here: it is the EXEC staging
                        area and the next "run" from the shell clobbers it

BRAM is single-cycle; SDRAM costs about six cycles against one. Code and
anything in a tight loop wants to be in banks $01-$04. Bulk data - samples,
images, big arrays - is what SDRAM is for.

Two traps that have already cost time on this port, both in PORT.md:
absolute addressing reads through the data bank register, and this
program runs with DBR = $00, so a table in bank $01 read with plain
absolute addressing silently returns bank-0 bytes. And $9F00 is I/O -
POKEing into it is how you reach the hardware on every other page here,
so it is a feature, but a stray pointer landing there will do something
visible rather than nothing.
