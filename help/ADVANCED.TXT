=== ADVANCED - game math, images, compression ===

The things that turn a BASIC into one you can write a game in. None of it
exists here; all of it exists as working assembly in X816_Library and as
working Forth in X816_DurexForth, so this page is mostly a porting list
rather than a design one.

--- fast math, for games ---

[ ] SIN8(a) / COS8(a) - a 256-entry sine table, angle 0-255, result
    -127..127. This matters more here than it looks: SIN and COS proper
    still throw (HELP MATH), and a table lookup is both available NOW and
    the right answer for anything moving on screen. Floating-point
    trigonometry per sprite per frame is not affordable at this speed.
[ ] ATAN2(dx,dy) - direction from one point to another, 0-255, 0 = east.
    The one function every chase-the-player enemy needs.
[ ] LERP(a,b,t) - interpolate, t = 0-255. Smooth movement without floats.
[ ] RNDSEED n - seed the generator so a level can be regenerated. RND
    works (HELP MATH) but there is no way to control the sequence, which
    makes a random level impossible to reproduce or to debug.
[ ] MIN(a,b) / MAX(a,b) / CLAMP(v,lo,hi) - small, missing, used constantly.

--- images ---

[ ] BMXLOAD file$,addr - load a BMX v1 image: palette into the palette,
    pixels into VRAM. The format the X16 tools emit, so there is a supply
    of art and converters already.
[ ] BMXSAVE file$,addr - write one back out.

If BMXSAVE reads the palette from VERA it will write bytes that are not
colours, because entries nobody ever wrote do not read back (HELP PAL) -
and loading that file installs them for real and the screen goes to
pieces. Keep the palette in an array and save that.

--- compression ---

[ ] ZX0 decompression - unpack data compressed by zx0 or salvador. A
    320x240 screen is 76,800 bytes and a BASIC program that wants three
    of them cannot afford them raw. Decompression also turns a slow card
    read into a fast one, which matters more than the space.

--- sound ---

[x] ENV v,a,d,s,r and ENVOFF v - attack, decay, sustain, release ticked
    once a frame across the PSG voices, so a note can fade instead of
    stopping dead. Built as designed, and documented in HELP AUDIOFM
    beside SOUND, which is what it changes the meaning of.

    Two things came out different from the sketch above. The tick is not
    only IRQ_POLL: WAIT, VSYNC and PLAY's note delay poll it too, because
    "SOUND : ENVOFF : WAIT 1000" is the first thing anybody writes and
    without those three it holds the whole release for a second and then
    collapses it in one step. And the poll applies as many steps as
    FRAMES have passed rather than one per call, so a slow program gets
    an envelope of the right length in coarser steps instead of one
    stretched to its own speed - capped at eight, so a long WAIT cannot
    walk hundreds of frames at once.

    The state is sixteen bytes a voice rather than eight: the level is
    8.8 fixed point and the three rates are steps in the same units. A
    four-second fade is a quarter of a level a frame, and an integer
    step can only be 0, which never arrives, or 1, which arrives in one
    second.
[x] ADPCM decode - about four times smaller than raw PCM. Built as
    ADPCMPLAY file$, documented in HELP AUDIOPCM beside PCMPLAY, which
    is the statement it is the compressed twin of.

    The open question was where the decoded audio goes, and the answer
    is a fixed buffer at $0A:0000 - the 384 KB between the staging
    buffer and $10:0000, which is the EXEC staging area and belongs to
    whatever runs next. So a compressed file is capped at 96 KB, and it
    is refused before anything is decoded rather than found out by
    overrunning. K_MEM_ALLOC was the tidier alternative and was not
    taken: the kernel allows 32 blocks and nothing here would free one,
    so a program that played ten sounds would run out of BLOCKS with
    megabytes free.

    It reads WAV files as well as raw streams, and that is correctness
    rather than convenience: an IMA WAV RESTARTS the predictor at every
    block, the block size is in the header and nowhere else, and a
    decoder that ignored it would drift into noise a fraction of a
    second in. A WAV also says its own sample rate, so ADPCMPLAY sets
    PCMRATE from it - the one thing PCMPLAY cannot do, because a raw
    sample does not say.

--- interrupts, which most of the above depends on ---

[x] ONVSYNC line-number - run a subroutine every frame.
[x] ONRASTER line,line-number - run one when the beam passes a scanline.
[x] ONCOLLISION line-number - sprite collision.
[x] RETIRQ - return from one. HELP SYSTEM has the full story and the
    limits, which matter here: these are DEFERRED to the next statement
    boundary, so they are for pacing and background work. A colour bar or
    a split screen needs IRQ 1,addr and machine code.

These three were the keystone. Animation timing, envelopes, PCM refill,
smooth scrolling and hit detection were all waiting on the same thing: a
way for BASIC to say "run this every frame". The kernel already had the
slots (K_IRQ_SET, eleven of them) and the dispatcher already saved and
restored VERA's ports around a handler, so the hard part was done. What
was missing was the BASIC side: re-entering the interpreter from an
interrupt safely, which is a real design problem and the reason this was
listed here rather than assumed.

The answer taken was not to re-enter it at all. The interpreter is not
re-entrant, and making it so would mean saving and restoring every
scratch global at an ASYNCHRONOUS boundary - the exact shape of the bug
that has cost this port four separate days. So the handler is entered
from the statement boundary instead, where nothing is half-built, and
the price is paid in latency rather than in a class of bug that only
appears when an interrupt lands on the wrong instruction.

That price is real and HELP SYSTEM states it plainly. What it buys is
that everything above can now be built: an envelope stepped once a frame,
a PCM buffer topped up, a sprite hit noticed - none of which needs to
happen AT the interrupt, only soon after it.
