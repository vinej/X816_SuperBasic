=== MOUSE - the pointing device ===

The mouse is real hardware on this machine and has been for a while: the
SMC serves mouse packets and the CPU reads them over the I2C bus on VIA
#1 (X816_core rtl/smc_x16.sv). It is not a KERNAL call, there is no ROM
involved, and durexForth already drives it - so nothing below is
speculative about the hardware, only about SuperBasic.

None of it is bound yet.

[x] MOUSE(n) - 0 the column, 1 the row, 2 the buttons (bit 0 left, bit 1
    right, bit 2 middle). One function with an index rather than three
    without, because a function taking no parentheses cannot be
    tokenized yet - see the note beside CURSORX in tokens.s.
[x] MOUSEAT x,y - put the pointer somewhere. There is nothing to tell
    the hardware: the controller only ever reports MOVEMENT, so the
    position is SuperBasic's own, accumulated here and clamped to the
    screen. This is how a game centres the pointer before it starts.
[x] I2CPEEK(dev,reg) - read any register of any device on the bus, and
    the reason the rest of this page could be written at all. The bus is
    bit-banged on PA0 and PA1 - genuine open drain, a line pulled low by
    making it an output and released by making it an input - and none of
    that can be checked with no mouse attached. But the system
    controller reports its own firmware version at $30 to $32, so

      PRINT I2CPEEK(&h42,&h30)

    prints 47: a number this code did not produce. A device that is not
    on the bus returns -1 rather than an invented byte.

    One thing to know before using it. A REPEATED start does not work
    here. A start is recognised only from the stopped state, so the
    textbook write-the-register-then-repeated-start-and-read is taken
    for a data bit and everything after it is nonsense. A full stop in
    the middle does work, and the device keeps the register number
    across it.
[ ] MOUSE on - switch the mouse on, zero the position, and ask the SMC
    for a wheel-capable device. MOUSE 0 switches it off.
[ ] MX - pointer column, clamped to 0-639.
[ ] MY - pointer row, clamped to 0-479. Y counts DOWN the screen, which
    is the PS/2 delta negated - a mouse pushed forward gives a smaller
    MY, not a larger one.
[ ] MB - buttons. Bit 0 left, bit 1 right, bit 2 middle.
[ ] MWHEEL - signed wheel movement since the last read. Reading CLEARS
    the accumulator, so two reads in a row give the second one nothing.
    Read it once per pass and keep the value.

There is no pointer on screen. The X16's KERNAL drew one with a hardware
sprite; nothing here does, so the arrow is yours to draw and move - which
is better than a pointer you cannot get out of your own way. A sprite is
the cheap way, HELP SPRITE, and it also means the pointer can be anything
you like.

What the SMC actually offers, for whoever writes this: command $21 reads
a four-byte movement packet (status, DX, DY, wheel) or zero when nothing
is pending; $22 reports the device ID, $03 for an Intellimouse with a
wheel; $20 requests a device ID; $42 is the same read as $21 but NACKs
instead of returning zero when the queue is empty. Deltas are signed and
relative, so MX and MY are an accumulator SuperBasic must keep itself -
the hardware has no notion of where the pointer is.

Each of MX, MY, MB and MWHEEL polling the SMC separately means four I2C
transfers to read the state once. That is fine at human speed and
wasteful in a loop; a single MOUSEPOLL that updates all four at once
would be the better shape if this turns out to matter.

THE MOUSE AND THE PADS SHARE ONE PORT. Both live on VIA #1 port A, and
the keyboard's I2C runs on PA0/PA1 of that same port. A joystick scan
must read-modify-write the direction register and leave those two pins
exactly as it found them, or it corrupts an I2C transfer in flight and
the mouse breaks from what looks like a mile away. HELP JOYSTICK.
