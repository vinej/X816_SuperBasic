=== TILE - tilemaps and display layers ===

A tilemap cell is two bytes: a tile code and a colour attribute
(foreground in the low nibble, background in the high one). The console
is itself a tilemap - layer 0, VRAM $00000, 128 cells to a row - so
writing cells is also how you paint the text screen without PRINT.

Two of the four keywords work now. They were written for VICKY's tile
engine and threw an argument error from phase 1.

TILEAT takes no layer number: it writes the console's map, which is the
one that is on screen, so a cell written is a character seen. It gained
an attribute argument instead -- placing a character AND its colours in
one statement, which PRINT cannot do. The layered form comes back when
TILEMAP can point a layer somewhere else.

[x] TILESET n,addr - point a layer at its tile graphics. Stored as the
    address >> 11, so a 2 KB boundary; a finer address would be rounded
    down in silence, so it is refused instead. The tile width and height
    share that register and belong to LAYERMODE, so this is a
    read-modify-write.
[x] TILEMAP n,addr - point it at its map. Stored as the address >> 9, so
    a 512-byte boundary, and refused the same way.
[x] TILESHOW n,on - enable or disable a display layer. Layer 0 is the
    console here, not layer 1 as on the X16, so TILESHOW 0,0 blanks the
    text screen. It comes back.
[x] TILEAT x,y,code,attr - write one cell of the console map. Address
    arithmetic is y*256 + x*2, because a row is 128 cells of two bytes.
    Codes are CP437 and the tile index IS the character code, so
    TILEAT 5,3,65,7 really does put a grey A at column 5 of row 3.
[x] TILEGET(n,x,y) - read a cell's tile code back. A function, so it
    takes parentheses: C=TILEGET(0,5,3). Unlike TILEAT it DOES take a
    layer number, because a layer whose map has been pointed elsewhere by
    TILEMAP is the one worth reading. The row stride comes from the
    layer's own config register rather than being assumed, so a 32-wide
    map reads correctly too.
[x] TILEATTR n,x,y,attr - write a cell's colour attribute, leaving the
    character alone. Foreground low nibble, background high.
[x] LAYERMODE n,cfg - the layer config byte. Colour depth 1:0 (0 is
    text), bitmap 2, 256-colour text 3, map width 5:4 and map height 7:6
    as 32, 64, 128 or 256 tiles. The console is mode 0.
[x] TMAPLOAD n,file$ / TMAPSAVE n,file$ - a whole map to and from a file.
    Self-sizing on save: the config byte carries the map's width and
    height codes and a cell is two bytes. A file bigger than the map is
    refused rather than wrapped around onto the console.

    TMAPLOAD 0 restores the WHOLE TEXT SCREEN to what it was when the
    file was saved, because layer 0 is the console. That is occasionally
    what you want and usually a surprise; a map of your own belongs on
    layer 1.
[x] TILELOAD n,file$ / TILESAVE n,file$,len - the tile graphics. Tile
    data has no inherent length, so saving asks for one - where the
    graphics stop is something only the program that drew them knows.
    A load is bounded only by the end of VRAM, which it is refused for
    running past.

VERA has two layers, 0 and 1, and both can be tilemaps. The X16 put its
text screen on layer 1; this machine uses layer 0, so code ported from
X16 sources will be pointing at the wrong one.

Layer 0's registers are $9F2D-$9F33 and layer 1's are $9F34-$9F3A, so a
layer is seven bytes and the code indexes by n*7. Read out of the
emulator's video.c, like everything else on these pages.

Careful with layer 0 while the console is live: the map at $00000 and
the font at $04000 ARE the text screen. Repointing MAPBASE at your own
map is the polite way to have both - the console keeps working, it is
just not being displayed - and TILEMAP 0,0 typed blind puts it back.
