=== FILE - the SD card ===

Real FAT32 on a real card. Paths are ASCII with "/" separators, and there
are no device numbers, no secondary addresses and no CBM DOS command
channel - none of that survived the move off the C64.

Everything on this page works. The kernel side is sixteen calls (K_FS_*
and K_DIR_*, KERNEL.md section 6) and all of them are bound.

[x] LOAD "name" - load a BASIC program, replacing the one in memory.

    THE FILE NEED NOT HAVE LINE NUMBERS. A line without one is given the
    next number going; a line with one keeps it and the numbering carries
    on from there, so a file may mix the two and an older file loads
    exactly as it always did. Blank lines are dropped rather than
    numbered - a numbered empty line DELETES the line it names.

    Either line ending works, CR or LF or both, so a program written in
    an editor on a PC or a Mac loads as it was written. HELP LANGUAGE.
[x] SAVE "name" - save the program. Creates the file, or TRUNCATES an
    existing one - there is no confirmation and no backup.
[x] BLOAD "name",addr - load raw bytes to an address, no header.
[x] BSAVE "name",start,end - save raw bytes. END IS INCLUSIVE: the last
    byte written is the one at end, so a single byte is start = end.
[x] DIR ["path"] - list a directory. With no argument, the current one.
    Names are shown in 8.3 columns with a size, and "D" marks a
    directory; long names are not shown as such.
[x] DEL "name" - delete a file.
[x] RENAME "old","new" - rename one. The new name is a BARE NAME, not a
    path: renaming across directories would mean writing the entry
    somewhere else, which the kernel treats as a different operation.
[x] COPY "src","dst" - copy one. Streams through a 512-byte buffer; the
    destination is created, or truncated if it already exists.
[x] BRUN "name",addr - load a machine-code file and call it.

    The address is NOT optional here, and that is the one place this
    machine departs from BASIC816. Upstream BRUN takes no address because
    the C256 loads PGX files, which carry their own; there is no PGX on
    the X816, and the one executable convention this machine has - the
    8-byte "X816" header - means $01:0000, which is where SuperBasic
    itself is running. Honouring it would have BRUN overwrite the
    interpreter mid-statement. So the caller says where, exactly as
    BLOAD does, and the person who assembled the binary already knows.

    The file is loaded verbatim: no header is expected and none is
    skipped. It is then called at its first byte with a JSL, so it must
    return with RTL and BASIC carries on afterwards - this is BLOAD and
    CALL in one statement, not a chain to another program. Whatever it
    leaves in A lands in ERR%.

    ERR% with the percent, and this catches everyone once: ERR, ERL,
    DOSSTAT and BIOSSTAT are created as INTEGER variables, and a bare
    name in an expression is looked up as a FLOAT. The lookup matches on
    type before name, so PRINT ERR answers "Variable not found" while
    PRINT ERR% answers the number. Stock BASIC816 behaviour, not this
    port's.
[x] CD "path" - change the working directory.
[x] PWD - print it.
[x] MKDIR "path" - create a directory.
[x] RMDIR "path" - remove an empty one.
[x] OPEN #n,"path","R" or "W" - open one of four channels. The mode is
    a string because a bare R would tokenize as a variable; only its
    first letter is read, so "READ" and "WRITE" work too. Re-opening a
    channel closes it first, or a program edited and re-run leaks a
    kernel handle every time round.
[x] CLOSE #n - close one channel. CLOSE on its own closes all four.
    A write channel is only flushed when it is closed, so a program that
    stops early loses the tail of its file. Every BASIC has worked this
    way; it is still the commonest way to lose data.
[x] PRINT #n, ... - everything PRINT can do, sent to a file: strings,
    integers, floats, the comma columns, the trailing semicolon. None of
    it is reimplemented. PRINT already routes every character through
    one sink, so PRINT # switches the sink and calls PRINT.
[x] INPUT #n, var [, var] - and the mirror image, filling the same
    buffer a typed line goes into. One value to a LINE, not to a comma,
    which is also what PRINT # writes.
[x] EOF(n) - true once a read channel has run out. True BEFORE the
    failing read, so WHILE NOT EOF(1) ... INPUT #1 ... WEND reads every
    line and stops, instead of processing one phantom empty line.
[x] SEEK #n,pos and LOC(n) - move a channel, and ask where it is.

    LOC is the position the PROGRAM is at, which is not the position the
    FILE is at: a read channel holds up to 256 bytes it has already been
    given, so the program is BEHIND by whatever is still unread, and a
    write channel is AHEAD by whatever is still waiting to go out. Both
    are accounted for. Neither keeps a counter of its own - seeking by 0
    from the current position returns it, so LOC asks rather than
    shadows, and a shadow that drifts is the kind of thing that goes
    wrong once and is never noticed.

    SEEK flushes a write channel first and throws a read channel's
    buffer away. Seeking past the end of a file is refused rather than
    growing it. Fixed-length records follow from this.
[x] LINPUT #n,var$ - a whole line, commas and all.

    LINPUT and not "LINE INPUT" as this page used to ask: LINE is
    already the graphics statement, and a tokenizer that matches
    keywords anywhere would read "LINE INPUT" as a call to draw one.

    The comma is the whole point. INPUT #1,A$,B$ splits on commas
    because that is what INPUT does, so a line of prose comes back cut
    into pieces. This reads to the end of the line and stops.

Channels are buffered a page at a time, so PRINT #1,X in a loop is not
one card transaction per character.

Numbers are written the way PRINT writes them, which means a leading
space in front of positive ones. Reading that back exposed a defect
inherited from BASIC816: a leading blank hangs the number parsers, from
the keyboard just as much as from a file. INPUT skips blanks first on
this machine now. The C256 build is left alone, so that it still
reproduces stock byte for byte.

A file is opened by path and returns a handle; reads and writes take a
parameter block. Errors come back with carry set and a KERR code in C,
which will need mapping onto BASIC error messages - "File not found" is
a friendlier thing to print than a number. Today every failure is the
same one word, whatever went wrong.

Two things about how this is wired, for whoever writes the rest.

The seam is narrow. dos.s reaches the card only through the Foenix
FK_LOAD/FK_SAVE/FK_DIROPEN/FK_DIRNEXT/FK_DELETE/FK_COPY/FK_RUN entry
points, so binding those in X816/kernel_x816.s lit up the statements
above without touching portable code. FK_RUN is the one that stayed a
stub: there is no PGX here, so BRUN does the work itself.

COPY has no kernel call behind it and rightly so -- a copy is a read
loop and a write loop with a buffer, and the kernel cannot know which
buffer a program can spare. It is implemented here, holding both files
open at once and streaming through CLUSTER_BUFF, the 512 bytes dos.s set
aside for the C256 kernel's cluster I/O and which nothing uses on this
platform. A short write is treated as a full card rather than ignored.

RENAME is not a binding at all -- the portable S_RENAME is guarded out
here and replaced. It renames by raw directory surgery: read the on-disk
entry, edit the 8.3 name in place, write the sector back. The X816 kernel
owns the FAT and hands out no sectors, so that cannot be made to work --
but unlike the C256's it has a rename call, so the statement is simpler
here than upstream, not harder.

DIR is the one that is not a straight binding. CMD_DIR walks RAW FAT32
records - it reads a 32-byte on-disk directory entry and picks the 8.3
name, the attribute byte and the size out of it - while the kernel hands
back a cooked one: a NUL-terminated "FOO.BAS", a directory flag and a
size. FK_DIRNEXT builds the former from the latter, which is why the
listing shows short names only. It also closes the directory handle at
the end of a listing and before starting a new one, because CMD_DIR
never closes anything and the kernel's handle pool is small.

The path does not always arrive in the same place, either. LOAD, SAVE
and DIR call SETFILEDESC and leave it in FD_IN.PATH; DEL calls
COPY2PATHBUF and leaves it in DOS_PATH_BUFF. Reading the wrong one gives
"Unable to delete file" for a file that is plainly there.

THE CARRY IS INVERTED across that seam. Every call site in dos.s reads
carry SET as success; the X816 kernel uses carry set for failure. The
first stub here returned SEC, which told dos.s that every load, save,
directory listing and delete had SUCCEEDED - so DIR printed whatever
happened to be in the entry buffer rather than saying it could not read
the card. The remaining stubs return CLC.

CD, PWD, MKDIR and RMDIR are NEW KEYWORDS, not ports. BASIC816 has no
tokens for them because the C256 kernel had no working directory at all.
Their tokens are appended at the END of the table in tokens.s, guarded to
this platform: token IDs are assigned by position from $80 up, so adding
at the end leaves every existing one where it was.

The working directory belongs to the KERNEL, not to BASIC. It is shared
with the shell, it survives leaving the interpreter, and every relative
path -- LOAD, SAVE, DIR, DEL -- resolves against it. A bare DIR passes an
empty path, which is how the kernel spells "here".

The exec cap is worth remembering when saving programs meant to be run
from the shell: "run" refuses an image over 65,280 bytes ($FF00). That
limit is on the interpreter image, not on your BASIC program, but a
turnkey build that bundles both hits it.
