# PORT.md — BASIC816 → X816 port sketch

Status: **design sketch, 2026-08-06.** No code yet. This expands the feasibility
study at `X816_core/doc/SUPERBASIC.md` (2026-08-03) into a concrete port plan:
source layout, memory map, kernel I/O bindings, the math-layer rewrite, and the
SuperBasic feature layer to add on top.

Companion reading, in order:
1. `X816_core/doc/SUPERBASIC.md` — the feasibility study (why BASIC816, obstacles, phases)
2. `X816_core/doc/KERNEL.md` — the kernel ABI this port binds to
3. `X816_core/doc/MEMORY_MAP.md` — address space and carve-outs
4. `X816_DurexForth/asm/x816.asm` — the most complete worked example of the kernel crossing
5. `X816_Library/src_acme/system/x816kernel.asm` — width-crossing discipline (its header comments)
6. `X816_core/tools/contract.py` — single source of truth for every kernel constant

## 1. Shape of the port

Base: **pweingar/BASIC816** (https://github.com/pweingar/BASIC816), Peter
Weingartner's 65816-native BASIC for the C256 Foenix. GPLv3, 64tass assembly.

*Naming trap:* FoenixRetro/f256-superbasic ("SuperBASIC") is a different,
65C02-only codebase. Not usable here. We port BASIC816 and brand the result
SuperBasic.

BASIC816 already has the porting seam we need: a `SYSTEM=` assembler define
selects a per-platform directory (`src/C256/`, `src/CBM/`) providing
`mmap_*.s`, `kernel_*.s`, `io_*.s`, `bootstrap_*.s`, platform statements and
platform math. The interpreter core (`interpreter.s`, `eval.s`, `tokens.s`,
`statements.s`, `variables.s`, `strings.s`, `heap.s`, …) is portable and — the
decisive point — already written for **native mode on a flat 24-bit machine**
with far pointers throughout. The port is:

- add `SYSTEM_X816` and a new `src/X816/` directory (§2),
- bind console/keyboard/files to the kernel jump table at `$00:FE00` (§4),
- replace the C256-silicon math layer with software routines (§5),
- emit a raw binary with the 8-byte `"X816"` header at `$01:0000` (§7).

Zero RTL changes. M10K is at 98%; a software-only port never touches it.

## 2. Source layout

Fork BASIC816, add `src/X816/` mirroring what `src/C256/` provides:

| `functions_x816.s` | platform functions (TIMER, KEY…) | |

## 3. Memory map

The machine is flat 16 MB, no banking. From `MEMORY_MAP.md` and the
feasibility study §4:

| What | Where | Notes |
|---|---|---|
| Direct page / globals | `$00:3000` | page-aligned (unaligned D costs +1 cycle per dp access); BASIC816's globals block is ≤256 B |
| Interpreter stacks (return / argument / operator) | inside `$00:3000-$00:9DFF` | 3 × 4 KB as on C256 fits easily |
| CPU stack | `$0100-$1FFF` (top `$1FFF`) | kernel convention; load S **16-bit only** — an 8-bit `txs` zeroes SH |
| Interpreter code | `$01:0000` + 8-byte header, entry `$01:0004` | banks `$01-$04` are single-cycle BRAM |
| Program text + heap | end of code … `$04:FFFF` | ≈190 KB BRAM after a ~64 KB interpreter |
| Bulk/expansion later | `K_MEM_ALLOC` arena `$20:0100-$DF:FFFF` | 32-block cap → grab one big block, sub-allocate; SDRAM is ~4.5× slower than BRAM |

Standing carve-outs to respect (bank 0): `$0000-$0021` C-runtime pseudo-regs
(kernel's VSYNC cursor handler uses them at interrupt time), `$0022-$0031`
kernel-clobbered scratch, `$2000-$2FFF` kernel, `$9E00` guard page (never a DP
base), `$9F00-$9FFF` I/O, `$FE00-$FEFF` jump table, `$FFE4-$FFFF` vectors.
Never park live data at `$10:0000+` — that's the EXEC staging area, clobbered
by the next `run`.

**DBR strategy:** run with `DBR = $00` (kernel convention; I/O page and bank-0
globals reachable with absolute addressing). BASIC816 was built for code in a
high bank with globals in bank 0, so it should already use long addressing
(`f:`) for in-code data — but **audit every absolute-indexed table read in the
code bank** (token tables, dispatch tables, keyword lists). The DurexForth
port's #1 lesson (`X816_Library/README.md` DBR audit): under `DBR=$00`,
indexed lookup tables assembled into bank `$01` are read from bank `$00`
**silently** — wrong bytes, no crash.

**Entry sequence** (`bootstrap_x816.s`; adapted from
`X816_DurexForth/asm/durexforth.asm:186-202`). `K_EXEC` guarantees only
native mode with M=0/X=0; D is still the shell's, interrupts are masked,
S and DBR are wherever the shell left them:

```asm
        rep #$30            ; 16-bit A/X/Y
        lda #DP_BASE        ; $3000
        tcd
        ldx #$1FFF
        txs                 ; 16-bit load of S — never 8-bit
        lda #0
        pha
        plb                 ; DBR = $00
        cli
        jmp COLD
```

Image header (first 8 bytes of the binary):

```
$01:0000  58 38 31 36        "X816"
$01:0004  5C xx xx 01        jmp long:COLD    ; entry
```

## 4. I/O hooks — binding to the kernel jump table

All I/O goes through the 64-entry `jmp long:` table at `$00:FE00`; call with
`jsl`, return `rtl`. ABI (normative, `KERNEL.md` §4): entry in native mode
**M=0/X=0**, up to three 16-bit args in C/X/Y (24-bit pointer = C low 16 +
X low byte), carry clear = success (result in C), carry set = failure
(`KERR_*` in C). Kernel preserves **only D and DBR**; A/X/Y/flags and
`$0022-$0031` are clobbered.

Mapping BASIC816's platform primitives (exact core-side symbol names to be
confirmed in Phase 0 against `src/C256/screen.s` / `kernel_c256.s`):

| BASIC816 primitive | Kernel call | Addr | Notes |
|---|---|---|---|
| screen putc | `K_CON_PUTC` (0) | `$00FE00` | see `$0D` trap below |
| print string | `K_CON_PUTS` (1) | `$00FE04` | NUL-terminated, 24-bit ptr |
| blocking key read | `K_CON_GETC` (2) | `$00FE08` | prefer GETKEY poll + cursor bracket, per DurexForth |
| key poll / INKEY$ | `K_CON_GETKEY` (3) | `$00FE0C` | 0 = none |
| CLS | `K_CON_CLS` (4) | `$00FE10` | |
| locate | `K_CON_GOTOXY` (5) | `$00FE14` | C=col, X=row (80×60) |
| cursor pos read | `K_CON_GETXY` (6) | `$00FE18` | |
| cursor on/off | `K_CON_CURSOR` (8) | `$00FE20` | arm only inside key waits |
| text color | `K_CON_COLOR` (9) | `$00FE24` | fg/bg 0-15 |
| LOAD/SAVE/OPEN/… | `K_FS_*` (16-30) | `$00FE40`-`$00FE78` | FAT32, ASCII paths with `/`, no device numbers |
| DIR | `K_DIR_OPEN/NEXT/CLOSE` | | |
| exit to shell | `K_EXIT` (33) | `$00FE84` | BASIC `SYSTEM`/`QUIT` statement |
| TIMER / TI | `K_TIME_GET` (50) | `$00FEC8` | free-running ms, 32-bit |
| frame counter | `K_IRQ_FRAMES` (52) | `$00FED0` | for `VSYNC`-style features later |

Encoding and behavioral facts that shape `io_x816.s`:

- **Charset is CP437/ASCII, not PETSCII.** `PRINT` needs no translation. No
  X16-style control codes — only `$08` BS, `$0A` LF, `$0D` CR are interpreted
  by `con_putc`.
- **The `$0D` trap:** on this console `$0D` is carriage-return-only (column 0,
  *same row*); `$0A` advances the line. Classic BASIC emits `$0D` for
  end-of-line — without translating CR→LF in the putc veneer, the REPL
  overprints row 0 forever. DurexForth's fix: `cmp #$0d : bne + : lda #$0a`
  (`asm/x816.asm:89-106`).
- **Key events are 16-bit:** `$0001-$00FF` = character; `$0100|n` = special
  key (arrows, F-keys) by IBM key position; `$0000` = none. First pass: mask
  `#$FF00` and ignore specials (DurexForth's `kern_getin`); later, map arrows
  for line editing.
- **Break (Ctrl-C):** Phase 1 = poll `K_CON_GETKEY` for `$03` in the
  interpreter loop's break check. Later option: the physical break key via
  `K_IRQ_SET` slot `KIRQ_NMI` (8) with a pending flag, as DurexForth does
  (`asm/x816.asm:108-129`) — the poll misses keys pressed while blocked
  inside a kernel key wait.
- **Width discipline** (from `x816kernel.asm`'s header, worth copying
  verbatim): one crossing point, not ninety — enter `rep #$30` before `jsl`,
  restore the interpreter's width on *every* path including errors; never use
  16-bit immediates in width-ambiguous code (stage args through DP); remember
  the hidden high byte of A is not zero on entry; carry is the kernel's
  verdict — don't destroy it on the way out.

## 5. Math layer (the one real rewrite)

Verified in BASIC816 source: `OP_FP_ADD/SUB/MUL/DIV` exist **only** in
`src/C256/floats.s` as pokes to the C256's memory-mapped FP coprocessor, and
int32 multiply drives GABE `M0_OPERAND_*` registers unconditionally.
`OP_INT_DIV` is an **empty stub even on C256** — audit how `/` actually works
there before assuming anything (repo `status.md` is stale).

Plan: `floats_x816.s` + `ints_x816.s` implementing the same `OP_*` interface
in software. BASIC816's float format is IEEE-754-single-shaped (1 sign, 8
exponent, 23 mantissa) — classic, well-trodden 65816 territory, and 16-bit
accumulator mode makes the mantissa loops respectable.

**Phase 0 correction:** `transcendentals.s` does *not* survive unmodified —
it contains 90 direct `FP_MATH_*` register accesses (the feasibility study
assumed it sat on the `OP_*` primitives). The rework is mechanical — replace
inline coprocessor sequences with `CALL OP_FP_*` — but it is real Phase 2
scope, not free.

Prior art in-tree: `X816_Library/src_acme/util/float` is a real software
float package (5-byte MFLPT format — different layout, but the
normalize/round/divide loop structure translates).

Fabric FP coprocessor: explicitly **not** for the first pass (drags RTL,
emulator, and hardware round-trips into a software-only project). Revisit
only if interpretation speed disappoints (ALMs at 46% have room; M10K does not).

## 6. 65816 traps checklist (already paid for by DurexForth — don't pay twice)

- 8-bit `txs` in native mode zeroes SH → always load S 16-bit.
- `jmp (abs)` fetches its pointer from **bank 0** regardless of DBR.
- Stack-frame reads like `lda $103,x` go through DBR → use stack-relative `lda n,s`.
- Native dp indexing wraps within **bank 0**, not the page — C64 `zp,x` wrap tricks are dead.
- Keep D page-aligned; `$9E00` is never a DP base.
- Opcode `$DB` is `dbg` in the emulator (STP on hardware) — never emit it.
- DBR vs code-bank tables — §3, the big one for a table-heavy interpreter.
- VERA palette does not read back reliably — keep shadow copies if graphics
  statements arrive in Phase 5.

## 7. Build, size cap, and test loop

**Toolchain.** 64tass is **not installed** on this machine (expected at
`X816_Library/64tass/64tass.exe`) — Phase 0 installs it. Build flags per
upstream `make_all.bat`: `64tass --long-address --flat -b --m65816` → raw
binary; the `"X816"` header comes from source (first 8 bytes of the image),
so file offset 0 = `$01:0000` with no Calypsi involvement.

**The 65,280-byte exec cap.** `run`/`K_EXEC` refuse files over
`X816_EXEC_MAX = $FF00`. The C256 build fits one bank, so we're plausibly
under — Phase 0 measures the real number. If over: bring up as `boot1.rom`
(uncapped), and/or implement the multi-bank copy fix `exec.s` already
documents.

**Emulator loop** (pattern from `X816_DurexForth/run-emu.sh`):

```sh
x16emu.exe -boot X816_core/boot/boot.rom -load F00000,kernel.bin \
           -sdcard scratch.img -autokeys 'run BASIC.BIN\n' -warp -gif out.gif
```

- Binary onto the FAT32 image via pyfatfs (no hardware in the loop).
- Headless verdicts: decode the final GIF frame against `font_cp437.s`
  glyphs for diagnostics, but the *real* channel is the guest exit code at
  `$9FBC` (emulator-only register; open bus on hardware) — add an
  `emu-exit`-style routine behind a detection check of `$9FBE/$9FBF`.
- `-autokeys` drops characters under load — drive test scenarios from an
  AUTORUN file on the card, not long key scripts.
- House rule: **every test ships with a negative control** that breaks the
  code under test and asserts the test then fails. BASIC816's own `tests/`
  directory is the Phase 2 corpus — exactly where a stale status doc could
  hide a vacuous green.

**Hardware loop.** `mkrelease.sh` → MiSTer SD; program is loaded from the
shell (`run BASIC.BIN`), ESC after exit reloads the shell. No RTL changes →
the sim suite is never involved.

## 8. The SuperBasic layer — what to add on top of BASIC816

BASIC816 is a classic line-numbered BASIC. The "SuperBasic" identity — a
beginner language that teaches structure instead of spaghetti — is a feature
layer added *after* the port is green, in the portable core (new tokens +
statement handlers), so it stays platform-independent:

| Tier | Feature | Notes |
|---|---|---|
| A (core identity) | `PROC name(args)` / `ENDPROC`, `LOCAL` | named procedures with parameters — the single biggest upgrade over classic BASIC |
| A | multi-line `IF / ELSE / ENDIF` | |
| A | `WHILE/WEND`, `REPEAT/UNTIL` | BASIC816 may have some already — audit `language.md` in Phase 0 |
| A | long variable names (beyond 2 significant chars, if base is limited) | |
| B (quality of life) | `RENUM`, `AUTO`, labels as GOTO/GOSUB targets | steps toward de-emphasizing line numbers |
| B | full-screen / line editor using arrow keys (`$0100\|n` events) and `K_CON_GOTOXY` | the 80×60 console makes a real editor possible |
| B | `TIMER`, `WAIT`, `KEY$`/`INKEY$` on `K_TIME_GET`/`K_CON_GETKEY` | |
| C (platform showcase) | `COLOR`, `LOCATE`, `CLS` (Phase 1 already), sound via YM2151, VERA/VERA2 graphics statements, `BLIT` | Phase 5; VERA2's linear framebuffer at `$E0:0000` makes `PSET`/`LINE` almost trivial |

Rule of thumb: Tiers A/B are edits to the portable core and benefit any
future target; Tier C lives in `statements_x816.s`/`functions_x816.s`.

## 9. Phases (aligned with the feasibility study §5)

- **Phase 0 — probe. DONE 2026-08-06** — see "Phase 0 findings" below.
- **Phase 1 — platform skeleton. DONE 2026-08-06.** `SYSTEM_X816` +
  `src/X816/` (8 files); software int mul/div came forward from Phase 2
  (the C256 math registers are the X816's CPU stack, and DIVINT10 drives
  decimal printing). Binary: 31,334 bytes. Milestone met in the emulator
  (`run-emu.sh`, with negative control): banner, `READY`, `PRINT 1` → `1`,
  `XYZZY` → `Syntax error`. Known phase-1 limits: floats THROW (so `/`
  throws too — it always promotes to FP), `RND`/`^` inert, DOS commands
  refuse, monitor BRK not wired.
- **Phase 2 — math.** §5. Drive BASIC816's `tests/` corpus with negative
  controls.
- **Phase 3 — files + full language pass.** LOAD/SAVE/DIR → `K_FS_*`/`K_DIR_*`;
  sweep the statement sheet; stub C256-only statements.
- **Phase 4 — hardware.** First as `boot1.rom`, then shell-run `.bin` once
  the size cap question is settled. One change per round trip.
- **Phase 5 — SuperBasic layer + platform showcase.** §8 tiers, in order.

## 10. Phase 0 findings (2026-08-06)

Setup: 64tass **1.60.3243** installed at `64tass/` (gitignored); BASIC816
vendored as a git subtree at `basic816/` from upstream commit `bea8847`.

**Build reproduces exactly.** The stock C256 FMX target
(`SYSTEM=2 C256_SKU=1`) assembles under 64tass 1.60 with 308 deprecation
warnings (cosmetic `@l` spacing), 6 passes, and produces a binary
**byte-identical to the upstream prebuilt**.

**Size: 53,918 bytes vs the 65,280-byte exec cap — 11,362 bytes headroom.**
Shell-run `BASIC.BIN` is viable from day one; the `boot1.rom` fallback is not
needed unless the port grows past the cap (X816 platform code replaces C256
code, so net growth should be small until the SuperBasic feature layer).

**The seam is even cleaner than hoped.** Hardware references in the portable
core: 115 total, **all of them math** —
`integers.s` 6 (GABE `M0_OPERAND` multiply), `floats.s` 19 (inline
`FP_MATH_*` pokes), `transcendentals.s` 90 (inline `FP_MATH_*` pokes).
Zero VICKY/keyboard/other-hardware references outside `src/C256/`. Only 11
`.if SYSTEM = SYSTEM_C256` conditionals across 5 core files.

**The console surface is 5 routines** (verified by grep over core call
sites): `SCREEN_PUTC`, `GETKEY`, `GETKEYE`, `CLSCREEN`, `INITIO`, plus
`UART_PUTC` behind the `BCONSOLE` device mask (`bios.s` `DEV_UART` — bind it
to `K_CON_PUTC` too, or strip the device bit) and the `LINES_VISIBLE` global
for pagination. All console output funnels through `bios.s` `IPRINTC`.

**`OP_INT_DIV` mystery solved: it's dead code.** `OP_DIVIDE`
(`operators.s:127`) unconditionally promotes to `OP_FP_DIV` — division is
always floating-point, the empty stub is never called. *But* integer divide
hardware IS used elsewhere: `DIVINT10`/`DIVINT100` (`utilities.s:300,344`)
poke the C256 `D1_OPERAND` divider inside `.if SYSTEM = SYSTEM_C256` guards
(with a literal `TODO: flesh out non-C256 division`). These drive decimal
number printing — so software integer divide is needed for the *first*
`PRINT 1`, i.e. it belongs to **Phase 1, not Phase 2**. Audit `MOD` when
implementing.

**Free code found:** a complete software 32-bit shift-add multiply already
exists at `integers.s:201-230`, commented out ("we don't have a hardware
multiplier, so do the multiplication the hard way") — resurrect it for X816.

**DBR outlook is good.** The house style accesses data tables with `@l`
long addressing (e.g. `HEXDIGITS` in `bios.s`), which is DBR-immune. The
full audit of indexed table reads still happens in Phase 1, but the style
suggests few or no landmines.

**SuperBasic layer, revised:** upstream already has `DO [WHILE|UNTIL] …
LOOP [WHILE|UNTIL]`, `BREAK`, and `BEGIN/BEND` blocks (`language.md`). Tier
A shrinks to named procedures (`PROC`/`ENDPROC`/`LOCAL`), multi-line
`IF/ELSE/ENDIF`, and long variable names.

## 11. Open decisions (carried from the feasibility study)

1. **GPLv3 — DECIDED 2026-08-06: accepted.** The repo is public
   (https://github.com/vinej/X816_SuperBasic) and GPLv3 as a whole; new
   own-copyright modules are dual-licensed GPLv3/MIT per README so they can
   flow back to the MIT X816 projects.
2. **Boot story.** Recommendation stands: shell remains the boot program,
   BASIC launches from it (`run BASIC.BIN`) — keeps BASIC an ordinary,
   replaceable program and leaves the Forth plan undisturbed.

   back; otherwise claim 3.
